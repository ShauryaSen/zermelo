# Noise sweep status, 16 Oct

Branch `bounds-harness`. Full spec is in `docs/noise-sweep.md`. This is the short version.

## What's running

Six noise levels, sigma = 0, 1.2, 2.4, 4.8, 7.2, 9.6 m/s. 32 seeds each. MPC only. Takes about 40 min.

To read it:

```
pixi run python -m zermelo.experiments.balloon_waypoint.metrics.ladder \
    mpc_noise_s0 mpc_noise_s12 mpc_noise_s24 mpc_noise_s48 mpc_noise_s72 mpc_noise_s96
```

## How the noise works

Truth stays ERA5. Only the forecast gets worse:

```
forecast = truth - noise(sigma)
error    = truth - forecast
W        = forecast + error = ERA5 again, exactly, at every sigma
```

New `problem.forecast = "noisy"` option next to your `"GEFS"` and `"gaussian"`. It uses its own random key
so nothing you've already run changes. This is what Sarah wanted: same ground truth on every line, noise
only in the forecast.

Also `resource_weight = 0` now, so the score is just navigation. The altitude cap still bites though —
typical episode spends 36 of its 40.

## Three things in the code that look wrong

I didn't touch any of these. Want your read first.

**1. The belief's amplitude is from the wrong record.** `amplitude=2.4` says it's the RMS of W - F in this
record. I measured it: 2.797 in u, 2.784 in v. The config is still called `ERA5_SH_JUL2021`, so I think 2.4
came from the old Southern Hemisphere record and never got updated. Makes the belief about 16% overconfident
from the start. Same at every sigma, so it moves all the lines together rather than bending the trend.

**2. The belief and the error model disagree about altitude.** The kernel uses a lengthscale of 3 levels,
so it expects the error to be similar up and down the column. But `GaussianError` draws every altitude
independently. Altitude is the only thing the balloon controls, so this is the worst possible direction to be
wrong in. Was that on purpose? I left it as is.

**3. The planner thinks it can reach anything.** `reachable = 1.000` — the value iteration table says every
candidate is within 20 steps. One of them was 6500 km away. A leg is 60 h, and at the fastest wind the
balloon actually flew (17 m/s) that's about 3700 km. The acquisition uses that table to price waypoints, so
it keeps sending the balloon after stuff it can't get to. Seed 2 sat at a flat 6500 km from its waypoint for
40 moves straight.

## Stuff I figured out

**The forecast column is definitely persistence.** `max |forecast[t] - truth[t-8]| = 0.0`, exactly zero. So
"GEFS" is just a mode name and the file is ERA5 shifted 24 h. That answers the question from the meeting.

**Added a proper navigation score.** The tables had arrival and steps walked but not the summed distance to
the waypoint, which is the thing the MPC is actually minimising. It's computed from the record afterwards
(positions, altitudes and the waypoint are all already saved), so no simulation code changed and none of your
existing numbers moved.

**But raw distance turned out to be a bad number to report.** At sigma 2.4 it came out 88445 km with a
standard deviation of 100308 — bigger than the mean. Reason: the waypoint chooser can pick anything, so a
seed that gets a far waypoint racks up distance no matter how well it flies. And since the forecast is what
the belief is built from, sigma changes which waypoints get picked — so raw distance would mix up "flew
worse" with "got sent further". Switched the headline to `gap closed`, which is `1 - final/initial` distance
per leg. Scale-free, caps at 1.

**Only scoring legs that actually had somewhere to go.** Two kinds get dropped:

- Legs where the waypoint was already inside the arrival radius. These end after one move having gone
  nowhere, and still count as arrivals. Seed 0's first leg: one move, 143 km to 143 km. Dropping these took
  arrival from 0.477 down to 0.388. Heads up — this affects any arrival rate from before, not just mine.
- Legs that were never reachable. Reported separately as `out of reach`, about 6% at sigma 2.4.

**Seeds 8 to 32.** An episode only finishes about 4 legs, so arrival is an average of 4 coin flips. With 8
seeds the standard error was 0.12, which is bigger than the gap between neighbouring sigma levels.

**My own bugs along the way**, so you know what to re-check: `dataclasses.replace` on `NAVIGATOR` (it's a
hydra dict, not a dataclass), wrong npz key names, and a reachability bound built from the record's max wind
— which is a 60 m/s jet way down at 14.8 km, so the bound came out at 13000 km and flagged nothing.

## Why the bounds aren't running yet

`V_plan <= V_mpc <= V_hind` only holds if all three are doing the same task. They're not: each arm has a
different belief (`hind` gets the true field, `plan` averages 32 draws), and each picks its waypoint from its
own belief. So they're flying to different targets and the ratio doesn't mean anything. Same problem with
arrival rate, so it's not about how I scored navigation.

For a real bound, all three arms need to share one waypoint sequence so the only difference is the navigator.
That's a change to how arms get built, not a sweep config. The arms are written and sitting unregistered in
`sweeps/bounds_noise.py`. `OpenLoopAgent` is in `methods/waypoint_bo/agent.py` and works.
